# 简体客户端 REA 逆向发现汇总（2026-11-21）

本文汇总本轮使用 REA/Ghidra 对简体客户端做只读逆向、再用 Frida 和抓包交叉
验证后得到的信息。目的是给后续协议、NPC、地图和稳定性规划提供依据，不是
“全客户端已经兼容”的结论。

## 结论摘要

除登录界面 BGM 一直被带入地图外，还确认了以下问题：

| 问题 | 当前状态 | 性质 |
| --- | --- | --- |
| 地图 BGM 不切换，持续播放 `music\01.ogg` | 已修复，用户实测正常 | 简体 `0x0002` 角色包过短，地图号越界读取 |
| 简体角色包缺少多个原生字段 | 已延长到完整读取范围 | 协议兼容基座问题 |
| 误弹交易密码、无法删除物品 | 已修复并通过专项测试 | 同一角色包越界读取 |
| 点击“补发天使”导致 NPC 语音空指针崩溃 | 已修复该具体 NPC，仍需全量审计 | 客户端缺少 NPC 原型时没有判空 |
| 地图过暗、光照异常 | 已按 CN profile 修复 | `0x0014` 光照包长度不足 |
| 角色未选阵营时 Angels GO! 被静默拦截 | 已按 CN profile 修复 | 服务端逻辑限制，不是 REA 直接发现 |
| 客户端“无响应” | 未闭环 | Frida 样本只看到等待态，不能证明死锁 |
| `START.EXE` 启动器访问冲突 | 未闭环 | 与 NPC 语音崩溃是分开的事件 |

最重要的协议结论是：简体客户端的 `0x0002` 处理器至少读取到包内偏移
`+0x1818`，所以任何构造出来的 `0x0002` 都不能短于 `0x1819`（含两个字节
opcode，共 6169 字节）。以前“按旧模板发一小段再补几个字段”的做法会持续
产生随机行为，BGM、交易密码和 UI 状态只是其中最先暴露的三个症状。

## 1. BGM 一直播放登录曲

### 现象

登录界面播放 `music\01.ogg`，进入地图后仍然继续播放登录曲。圣光城
（stage 3）在 `stage.xml` 中有专属配乐：

```text
配樂檔1 = music\03.ogg
配樂檔2 = music\04.ogg
```

简体数据位于 `extracted_paks/update29/setting/gb/stage.xml`，繁体参考数据位于
`extracted_paks/update26/setting/big5/stage.xml`，两个版本对 stage 3 的 music1
和 music2 一致。

### 根因

登录 BGM 在 `FUN_004BF3F0` 中固定调用：

```text
FUN_0081D870("music\\01.ogg", 100, 1, 1, 1)
```

地图 BGM 选择在 `FUN_005B03E0`，读取链路是：

```text
FUN_005B03E0
  -> self + 0x3c8             玩家对象
  -> player + 0x20cc          stage
  -> 以 stage 查 stage record
  -> record + 0x18            music1
  -> record + 0x1c            music2
  -> FUN_0081D870(path, ...)  真正播放
```

当前 `cn-8.6.5.7` 客户端的 `0x0002` 角色处理器 `FUN_005E74B0` 读取：

```text
packet + 0x1773  -> player + 0x20cc
```

角色包过短时，`+0x1773` 会读到包外内存。BGM 修复前的运行时值为：

```text
stage = 804243502 = 0x2FEFC82E
低 16 位 = 51246
```

`51246` 查不到 stage record，`FUN_005B03E0` 不会得到有效配乐路径，于是
不会切歌，登录曲 `01.ogg` 继续播放。

还要注意 `FUN_005B03E0` 用 `DAT_00A41C58` 缓存“当前音乐路径”。相同路径不会
重复调用播放函数，所以只看到“没有新的 play 调用”不能直接判断 BGM 逻辑没有
执行，必须同时看 stage 和这个缓存路径。

### 修复

`server/seguridad_comercio.py` 将简体角色包补到：

```text
CN_CHARACTER_PACKET_SIZE = 0x1819  # 6169 字节，含 opcode
CN_PASSWORD_FLAG_OFFSET  = 0x1761
CN_STAGE_OFFSET          = 0x1773
```

`server/login.py` 的 `_ficha()` 最后统一经过 `ajustar_ficha(bytes(crudo), p.stage)`。
因此进入地图和热刷新角色信息走同一套长度、交易 PIN 和 stage 修正。

### 实测结果

修复并重启服务端后，Frida 事件记录到：

```text
play-stage-music-entry:
  stage = 3
  recordMusic1 = "music\\03.ogg"
  recordMusic2 = "music\\04.ogg"

music-play-call:
  path = "music\\03.ogg"
```

用户随后实测确认圣光城 BGM 正常。运行时事件保存在
`scratch/bgm-probe-events.jsonl`。

### 重要纠正：`+0x40c` 是小时，不是天气

现有 Frida 探针里有一个字段命名为 `weather`，实际读取的是
`self + 0x40c`。`FUN_005B54B0` 会把传入值对 24 取模后写入该位置，所以它是
**小时**，不是天气类型。

`FUN_005B03E0` 的选择逻辑是：

- 小时在 7..18（含端点）时优先 `music1`；
- 小时小于 7 或大于 18 且 `music2` 非空时使用 `music2`。

本轮测试时小时为 12，所以选择 stage 3 的 `music\03.ogg`。不要把这个字段继续
写成 `weather=12`，也不要用它解释天气。

真正的天气字段在 `0x0014` 地图光照包中：

```text
包内 +6  u8   小时
包内 +7  u8   天气类型
包内 +8  u8   天气强度
```

## 2. 简体 `0x0002` 角色包的真实读取范围

`FUN_005E74B0` 的字段读取不止交易 PIN 和 stage。以下是本机
`cn-8.6.5.7` 客户端反编译中已确认的读取点（偏移均从 opcode 开始计算）：

| 包内偏移 | 读取形式 | 去向/用途 | 确认程度 |
| --- | --- | --- | --- |
| `+0x754` | u8 | `FUN_007F1F00` 数值输入 | 已见反编译 |
| `+0x755` | 0x1000 字节 | 复制到 player + `0xb8c` | 已确认；包含生产配方位图等大块数据 |
| `+0x1755` | u32 | 写入 UI/状态对象 `+0x6228` | 已见反编译 |
| `+0x1759` | u32 | 写入 `+0x568` | 已见反编译 |
| `+0x175d` | u32 | 写入角色对象 `+0x4dc` | 已见反编译 |
| `+0x1761` | u8 | 交易密码状态 `+0x278` | 已确认 |
| `+0x1762` | u8 | 写入 `+0x1b8c` | 已见反编译 |
| `+0x1763` | u32 | 写入 `+0x1193c` | 已见反编译 |
| `+0x1767` | u16 | 写入 `+0x11940` | 已见反编译 |
| `+0x1769` | u16 | 写入 `+0x11944` | 已见反编译 |
| `+0x176b` | u32 | 传入 `FUN_00600150` | 已见反编译 |
| `+0x176f` | u32 | 传入 `FUN_00600150` | 已见反编译；十进制 5999 |
| `+0x1773` | u32 | player + `0x20cc`，即 stage | 已确认 |
| `+0x1777` | 0x80 字节 | 复制到 `+0x1b90` | 已见反编译 |
| `+0x17f7` | 0x20 字节 | 复制到 `+0x1c90` | 已见反编译 |
| `+0x1818` | u8 | 写入全局 `DAT_00961DF8` | 已见反编译 |

最后一个读取 `+0x1818` 是 6168，因此完整包的最小长度是
`0x1819`（6169 字节，含 opcode）。这个长度不是“为了补丁好看”随手加的，
而是由客户端真实读取范围决定的。

### 包长演进，避免时序混淆

| 阶段 | 包总长 | 结果 |
| --- | ---: | --- |
| 最初旧模板 | 4120 字节 | `+0x1761` 已经越界，可误判交易 PIN |
| 交易 PIN 修复后 | 5986 字节 | `+0x1761` 可读，但 `+0x1773` 仍越界 |
| BGM/完整范围修复后 | 6169 字节 | 覆盖到 `+0x1818` |

因此“旧包 5984 字节”通常指交易 PIN 修复后、BGM 修复前的 body 长度；再往前的
最初包只有 4120 字节。两处日志/文档如果看起来数字不同，不一定是矛盾。

### 后续约束

1. 所有简体 `0x0002` 构造入口都必须调用 `ajustar_ficha()`，不能只改登录入口。
2. 新增角色字段时，先确认它是否会改变包长或与既有偏移重叠。
3. 不能把当前“旧模板 + 补零 + 修正几个字段”当成完整的简体原生 schema；
   未知字段仍然依赖客户端容错。
4. 如果以后加入新的 UI/状态字段，应先做同一套 Frida 读取验证，再改服务端。

## 3. 交易密码误弹与删除物品

这是同一角色包问题的早期症状。简体客户端 `0x0002` 处理器在
`0x005E87AD` 读取 `+0x1761`，写到客户端交易密码状态 `this+0x278`。
旧包只有 4120 字节，这个位置完全在包外，客户端偶发读到非零值后进入交易密码
验证窗口。

修复策略：

- 简体包补足到 6169 字节；
- `+0x1761` 明确清零，表示本服不启用独立交易 PIN；
- 收到长度为 136 的 `C2S 0x0049` 时，用原生消息 906 同步“未设置交易密码”；
- 不保存用户输入的数字，不修改登录密码，不代替真正的删除确认。

专项测试：

```powershell
.\.venv\Scripts\python.exe -m pytest tools/test_trade_password_cn.py -q
```

本轮复查结果：`10 passed`。

详细背景见 `docs/CN_TRADE_PASSWORD_2026-11-20.md`。

## 4. NPC 语音空指针崩溃

### 已确认的崩溃

2026-11-20 21:27 左右点击“补发天使”后，客户端在 NPC 语音回调中崩溃：

```text
EIP = 0x005BBCC4
读取 [EDX + 0xF8]，此时 EDX = 0
所在函数：FUN_005BBB80
NPC 原型：24801（Reissue Angel / 补发天使）
外观：40002
```

`FUN_005BBB80` 调用 NPC 原型查找函数 `FUN_004B01C0`。查找失败时返回空指针，
但后续代码没有判空，直接按语音槽位读取 `+0xF8`、`+0xFC` 等字段，然后拼接
`voice\%s.ogg`。

简体客户端 `setting/gb/npc.xml` 缺少原型 `24801`；同一资料表中存在原型
`14231`（补偿天使，外观同为 40002，且没有语音字段）。因此服务端在
CN profile 下只对这一个角色做报文层兼容：

```text
24801 -> 14231
显示名：补发天使
```

实体 ID、位置、外观、类别和服务端点击逻辑保持不变；服务端仍按原实体处理
补发对话和奖励。详细说明见 `docs/CN_NPC_CRASH_2026-11-20.md`。

### 这不是单点问题

客户端函数本身没有对 `FUN_004B01C0` 的返回值判空，因此任何“服务端有、客户
端 NPC 资料表没有”的原型，只要走到语音回调，都可能触发同类空指针。当前只
修复了已复现的 24801，**不能据此宣称全量 NPC 已经安全**。

后续建议：

- 扫描服务端所有 NPC 出生原型；
- 与 `update29/setting/gb/npc.xml` 做集合差；
- 对差集中的普通 NPC 建立明确的兼容映射或服务端禁用策略；
- 对已有映射做“客户端目录中目标原型必须存在”的启动检查；
- 用抓包回放验证每个地图的 NPC 出生批量。

## 5. `0x0014` 地图光照/天气包

简体客户端处理器 `FUN_005EF0E0` 的读取布局：

| 包内偏移 | 类型 | 用途 |
| --- | --- | --- |
| `+2` | u32 | 地图 flags；bit `0x20` 会关闭 minimap |
| `+6` | u8 | 小时，交给 `FUN_005B54B0`，按 24 取模 |
| `+7` | u8 | 天气类型，交给 `FUN_00687AF0`；0 表示无天气 |
| `+8` | u8 | 天气强度 |
| `+9` | i32 | 光照 preset；-1 表示不使用 preset |

旧包 body 只有 7 字节（含 opcode 共 9 字节），但客户端会读取 `+9` 的 dword，
等于越界读取。旧的小时字节 `0xFF` 也会被取模成 15，并不是“全亮”标志。

CN profile 现在发送完整的 11 字节 body（含 opcode 共 13 字节）：

```text
hour = 12
weather type = 0
weather intensity = 0
lighting preset = -1
```

这样客户端使用地图自身的亮度设置，不会强制打开或关闭某个光照 preset。
详细说明见 `docs/CN_MAP_LIGHTING_2026-11-20.md`。

## 8. 尚未闭环的问题

### 8.1 客户端“无响应”

本轮 Frida attach 到客户端后采集了 11 个线程快照，主线程：

- 10 次停在 `ZwDelayExecution / SleepEx / Sleep`；
- 1 次停在 `NtDxgkSubmitPresentToHwQueue`；
- 其他线程主要停在 `NtWaitForWorkViaWorkerFactory` 和
  `ZwWaitForMultipleObjects`。

这些样本只能说明主线程在等待或提交渲染，不能证明死锁，也不能证明声音线程是
根因。当前没有足够证据把它和 NPC 崩溃、BGM 修复或某个具体包绑定。

下一步需要：

1. 在用户实际遇到“无响应”时记录时间点、当前地图和最近操作；
2. 同时抓完整主线程栈、窗口消息泵状态、服务端最近收发包；
3. 区分“窗口未刷新”“网络未返回”“D3D present 卡住”和真正的死锁；
4. 不要在无法复现时仅凭 `Sleep`/`Present` 等待就下结论。

参考文件：`scratch/rea-results/hang-frida-status1.json`、
`scratch/rea-results/mouse-probe-status2.json`。

### 8.2 `START.EXE` 启动器访问冲突

Windows 记录到 `START.EXE` 在 21:21:43、21:22:15 的访问冲突。这两个时间点
早于 21:23 进入游戏的会话，不能归因于补发天使 NPC 修复，也不能归因于
`0x0002` 修复。

目前只知道是启动器崩溃，尚无完整的启动器栈、PAK/版本和本地更新服务器日志。
如果后续继续排查，应单独建立 `START.EXE` 问题记录，不要和客户端地图崩溃混为
同一个问题。

### 8.3 schema 仍未完全还原

当前简体 `0x0002` 仍然是“旧模板 + 长度补齐 + 关键字段覆盖”的方案。它足以
通过已验证的登录、地图、交易 PIN、BGM 和 UI 流程，但不等于已经理解每个原生
字段。

后续需要避免：

- 把“当前没有崩溃”当成字段全部语义正确；
- 直接把 IGG/繁体客户端的偏移复用到简体客户端；
- 在没有运行验证的情况下改 `+0x755` 之后的共享大块字段；
- 只测一次登录就宣称兼容所有地图和所有 NPC。

### 8.4 尚未完整解释的函数

REA 过程中也查看了 `FUN_005E30B0` 等较大的处理函数，但目前只能确认部分调用
关系，不能把整个函数当成已验证的协议说明。后续如果要做完整的 CN schema，
应以函数调用图、运行时读取点和抓包三方面交叉验证后再写进实现。

## 10. 后续优先级建议

### P0：稳定性

1. 做全量 NPC 原型审计，优先检查所有会触发语音的普通 NPC。
2. 把 `0x0002` 最小长度设成不可绕过的构造约束，并给其他 CN 包入口加同样的
   长度检查。
3. 复现客户端无响应，采集真正的卡死现场，不要用等待态样本推断死锁。
4. 单独排查 `START.EXE` 启动器崩溃。

### P1：协议正确性

1. 从 `FUN_005E74B0` 的读取点反推完整的 CN `0x0002` 字段表。
2. 对 `+0x755` 的 0x1000 字节生产配方位图、`+0x1777` 的 0x80 字节和
   `+0x17f7` 的 0x20 字节做运行时对比，确认服务端当前填值是否符合预期。
3. 继续整理 `0x0014`、`0x0002`、NPC 出生包之外的 CN 差异，不要把所有问题都
   塞进同一个补丁函数。

### P2：可维护性

1. 把“CN 原生偏移”和“服务端业务字段”分开命名，避免出现
   `weather` 实际表示 hour 这类误导。
2. 在文档和测试中记录包长演进，避免后续把 4120、5986、6169 三个数字混用。
3. 把 Frida 探针脚本和事件日志保留为可重复验证的证据，不把日志里的临时变量名
   当成协议名称。

交易密码误判和多个 UI/状态字段异常。当前修复已经覆盖已验证流程，但完整的 CN

已经完成的全客户端兼容。
