# 简体客户端误弹交易密码 / 无法删除物品

## 现象与日志

2026-11-20 18:51:56至18:52:52，客户端反复发送 `C2S 0x0049`，请求体长度136字节。服务端没有对应处理，日志只显示 `sin esquema`，没有收到后续的正常删除请求 `C2S 0x0013`。

窗口是独立的“交易密码”验证，不是登录密码。当前服务端只有登录密码和房屋密码实现，没有账号交易PIN字段、设置流程或可供用户查询的交易密码，不能让用户猜一个所谓默认交易密码。

## 根因证据

只读分析 `scratch/angel-cn-unpacked.exe`，它是本机简体8.6.5.7客户端的诊断副本；没有修改安装目录的客户端。

- `extracted_luas/item.lua` 中，拖到垃圾桶先调用 `game.dosafeverify(4)`，通过后才创建删除确认窗口，最终确认才调用 `game.destroyitemslot`。
- 简体客户端 `0x0002` 处理器 `0x005E74B0` 在 `0x005E87AD` 读取完整报文（含opcode）的偏移 `0x1761`，即5985字节，并将此字节写到交易密码状态 `this+0x278`。
- 旧服务端角色报文只有4120字节，没有覆盖5985；客户端读到包外数据，可误认为设置了交易密码。不是数据库里真的存在一个用户忘记的PIN。
- 验证函数 `0x005BD400` 在状态字节为0时直接返回1，允许进入原本的删除确认流程。
- 通知处理器 `0x005ED1F0` 的消息906（`0x38A`，见 `0x005ED29E`）明确把 `this+0x278` 清零；没有伪造一个密码验证成功，也没有直接执行删除。

## 修复策略

仅对显式配置 `AO_CLIENT_PROTOCOL=cn-8.6.5.7` 生效：

1. 角色报文补足至至少5986字节，5985位置明确为0，表示此本地服不启用独立交易PIN。已有报文内容、后续字段及其他客户端profile保持原样。
2. 对已经误入密码验证流程的已登录角色，收到136字节的 `0x0049` 后用原生消息906同步“未设置交易密码”状态；不保存输入的数字、不修改登录密码、不删除物品。用户关闭旧窗口后重新拖入垃圾桶，仍需正常确认。
3. 不实现交易PIN设置/修改能力，也不宣称这是独立的账号安全保护系统。若以后需要公网或多人服交易PIN，必须补充真实的存储、认证及敏感操作校验，不能把本地兼容策略当成验证实现。
4. 真正删除仍走 `0x0013`，检查背包格与物品ID一致，并保留携带装备宠物的保护逻辑。

## 验证与上线

`tools/test_trade_password_cn.py` 覆盖角色包完整性、原始字段保留、其他profile不变、首次进图和刷新、错误验证窗口恢复、不改物品或密码、畸形报文拒绝、未登录不处理、正常删除需匹配物品格与ID。

测试只使用临时数据库。没有为了验证删除用户真实背包中的道具，没有清空账号或角色。运行中的服务端需在玩家退出、存档完成后重启才能加载修改；客户端需要重新登录。客户端最终界面还需用户验证。
